# Upstream convergence watchlist

Where upstream T3 Code is building toward the areas J5 owns. Each entry says what upstream has, where J5 stands, and what would make us adopt upstream's version or change our own. Rewrite this file at every upstream advance (see [Merging upstream](../process/upstream-merge.md)); the line below names the upstream release it was last checked against.

Checked against `pingdotgg/t3code` nightly `v0.1.1-nightly.20261017.3238` @ `70d60e03a7`: upstream's first stable release with V2, v0.1.0, plus 197 commits.

## Agent-to-agent messaging and control

Delegated-question routing rechecked on 2026-10-20 at upstream commit [`c911f654b9`](https://github.com/pingdotgg/t3code/blob/c911f654b9fb604e93808c4cb216eb0e99825878/apps/server/src/orchestration-v2/DelegatedTaskQuestionReactor.ts). Its reactor still resolves parents through delegated tasks and native lineage, leaving J5 placement to J5.

- **Upstream:** the orchestrator MCP toolkit can send into another thread, wait on it, interrupt it and launch threads (`t3_thread_send`, `t3_thread_wait`, `t3_thread_interrupt`, `t3_thread_launch`, `create_threads`), answer another thread's pending requests (`t3_pending_request_respond`) and reconfigure it (`t3_thread_configure`). Thread tools reach any thread in the environment. Every tool declares who may call it, including writes that belong to no thread, such as a pull request's review guide. An agent outside the app can sign in to the MCP server with OAuth; a full-access sign-in may also change environment preferences and clone repositories. Messages sent by agents carry `senderThreadId` and render "Sent by another agent" with a link, and a wake the app writes itself, such as a restart continuation, renders as a notice from the app. Agents link threads to the person as `t3-thread://v1/<id>`, and `request_secret` blocks a turn until the person enters a secret privately. A delegated child's question now wakes its parent and ends a blocking wait, and the parent can answer it through the pending-request tools. A message to a finished delegated child starts a fresh task in it that notifies the parent when done. The later [async-question fix](https://github.com/pingdotgg/t3code/pull/15430) adds a blocking hint to pending-request summaries so working agents can keep working; it does not add placement-based parent routing. Revoking a session, or its expiry, closes the sockets it has open.
- **J5:** a ledger for each project, addressable participants, Exchanges (asks and replies), Inbox and delivery receipts. J5 follows upstream's access model, its environment-wide reach and its outside-agent sign-in ([divergence D2](upstream.md)). It still hides upstream's send, wait, interrupt and launch tools; the exact list is pinned by the registration test. An outside agent is a participant in J5's ledger, sends with `j5_send_message` and starts agents with `j5_spawn_agent`, capped by the level approved at its sign-in. A Crew seat asks its Captain rather than the person. Native questions that still arise on J5-spawned Peer Agents or live seats notify their placement parent with upstream-style pending-request guidance; queued notices cancel when the question resolves. Delegated children retain upstream's reactor. Actionable native questions on J5-spawned agents also reach the human Inbox as links to their original thread forms. Pending-request answers follow upstream's mode checks and response records, with no additional parent-only restriction, responder identity or ledger act. Parent agents finish their turns to receive notices; `t3_thread_wait` stays hidden, while upstream's delegated-task wait can return on a blocking question. J5's platform notices are stored as system messages, so upstream's notice label does not reach them.
- **Watch for:** reply or ask semantics, an inbox, responder attribution, or delivery guarantees upstream. Routing a child's question to its parent is the first of these, for delegated children only; if upstream does the same for top-level threads an agent started, J5's Crew-seat question rule and Exchanges could sit on top of it. An outside client that can _receive_ messages would be upstream's version of the Inbox. Any of those is the signal to rethink the J5 verbs as a layer on top of upstream's.

## Launch, workspaces and parallel agents

- **Upstream:** workspace-aware launches (new worktree, existing worktree, project root), configurable branch names with a prefix setting, tracked worktree setup and clone progress. A "No project" (Scratch) project exists in each environment for threads started without one; it is hidden when the server's state lives inside a checkout, which includes every J5 dev worktree. Multi-model send starts the same first message on several models, each in its own worktree, for comparing outputs. New since the last check: `delegate_task` can give a child its own worktree, started from the parent's local commit with project setup run; providers can be turned on or off per project; and storage cleanup can remove settled threads' worktrees, keeping any worktree an active thread still shares, and delete a pull request's branch after it merges or closes.
- **J5:** `j5_spawn_agent` and Crews create Peer Agents with briefs. A spawn joins the caller's project, another project, or upstream's "No project" project, and takes a permission choice within the caller's own and attachments, as upstream's launch does. Every Peer Agent and seat names its workspace: the caller's checkout, an existing worktree, or a new worktree prepared through upstream's ThreadLaunch on a thread J5 has already created and placed; a spawn may also name the project's main checkout. J5 still doesn't expose `t3_thread_launch` or `create_threads`. J5's `delegate_task` takes upstream's worktree option as upstream ships it. Multi-model send is refused from a persona draft, because a persona locks its model. J5 accepts upstream's "No project" project as shipped.
- **Watch for:** grouping or coordination of fanned-out threads, which would come close to Crews. A delegated child with its own worktree is now a Peer Agent in all but the person's direct line to it; if upstream lets the person work with a delegated child as an ordinary thread, the two shapes converge.

## Lineage, subagents and fleet views

- **Upstream:** a thread-details panel with a Lineage section, lineage hover cards, one collapsible subagent card per turn, and subagent history in workspace cards. Stop is a command of its own (`thread.stop`): it interrupts the turn, holds the queue, ends pull-request watches and stops the thread's delegated children. Lineage has a Stop control, and `task_cancel` stops a child the same way. New since the last check: a breadcrumb back to the parent thread; Claude workflows in Lineage, grouped by phase with their members, which a person or an agent (`t3_workflow_stop`) can stop without stopping the thread; a native subagent that can be stopped without its owner; Muse Code and Copilot subagents in child threads of their own; and a Waiting status with a timer in the sidebar. Upstream's copy calls the sidebar's active section "the inbox", which is not J5's Inbox.
- **J5:** placement and provenance, the Fleet page, sidebar spawned-children and Crew chips, persona identity on lineage and subagent rows. Upstream's Lineage panel shows none of J5's command relationships. `j5_stop_agent` and Crew stop send upstream's `thread.stop`.
- **Watch for:** cross-thread grouping beyond one thread's subagents, or an attention queue across threads. Either would mean upstream is approaching the placement tree, the Fleet page or the Inbox. Claude workflow phases are the first grouping beyond single subagents, still inside one thread.

## Handoffs and history transfer

Two different things share the word "handoff". J5 docs call upstream's history transfer a **context handoff** and J5's persona document a **handoff artifact**.

- **Upstream:** context handoffs (upstream's "portable handoffs") move a budgeted slice of history (`ContextHandoffBudget`) into a new provider conversation when a thread switches model or provider, is forked, or restarts portably; picking another model now shows the handoff that will happen. A failed native resume still falls back to a fresh conversation without telling the person.
- **J5:** persona handoff artifacts under `handoffs/` in project artifacts, with a nudge worker and a composer chip. The native-resume patch refuses a silent context handoff except when the conversation is gone ([divergence D6](upstream.md)).
- **Watch for:** upstream starting fresh only when the provider reports the conversation gone, and telling the person. That retires D6.

## Steering and queues

- **Upstream:** a queue-or-steer follow-up setting, a shared composer dispatch, editing, reordering and promoting queued messages, and held queues after a restart. Stop and a provider failure hold the queue too. Scheduled tasks bound to a thread queue instead of steering. A delegated task's completion steers its parent only when the session says steering doesn't interrupt tools (`activeSteeringInterruptsTools`). New since the last check: a steer no longer ends running subagents. Before a steer, Claude moves the parent's foreground subagents to the background, but the steer still cancels the turn's other running tool calls. Codex and OpenCode take a steer whose model selection changed without restarting the turn, and apply the new selection on the next turn. Cursor still steers by interrupting and restarting.
- **J5:** follows upstream's steering and queues. Agent-to-agent deliveries queue behind a running turn by default, with the GPT 6 and Claude exceptions (Claude's waits for the running tool calls), and a sender may ask for upstream's `steer` or `restart` ([divergence D4](upstream.md)); upstream's `auto` is not offered, and the default is revisited in January 2027. A J5 delivery to an agent whose queue is held resumes the queue and joins the back, unless the thread stopped on a usage limit or after a failed worktree setup, when it waits unsent. A delivery to a thread whose failed worktree setup left no held queue is accepted and held there by upstream. Agents have upstream's queue tools; an agent edits only a queued message it sent, inside its envelope. The remaining steer UX gaps are in the give-back backlog.
- **Watch for:** D4 can go when upstream steers without cancelling running tool calls on Claude and without restarting the turn on Cursor. This range moved both Claude and Codex toward that; Claude's tool calls and Cursor's restart remain. J5's own Claude exception (case 84) does it with priority `"next"`. Upstream's open #21158 queues agent sends to a session whose steering interrupts tools, which Claude's still reports; if it lands, check that J5's Claude peer steers don't take that path.

## Long-running autonomy

- **Upstream:** a Limited state for usage limits, snoozing until the reset, opt-in auto-resume, scheduled tasks across environments on a shared Scheduler, startup failures that retry and then fail visibly, pull-request watches that wake a thread on checks, reviews or conflicts, webhook-triggered schedules held by the relay while the server is offline, an agent settling its own thread at the end of its turn, an auto-settle opt-out for a thread, and a project script that runs when a thread settles. New since the last check: interrupted threads continue after a restart by default, stopping after three automatic continuations in a row and skipping a thread that waits on the person; a run whose provider stream ends without finishing fails visibly; inactivity auto-settle can keep threads that have a pull request; snoozed threads take queued automatic wakes; only one server can use a home at a time; on Linux each agent runs in its own systemd scope, so an out-of-memory kill spares the server; and a restart wakes a thread whose subagents' background work it cut.
- **J5:** follows all of it. A Crew seat may settle itself, and a Captain's settle carries its seats ([divergence D14](upstream.md)). A message from another agent holds a merged thread open, as a person's does ([divergence D30](upstream.md)). A stopped agent is not continued after a restart. J5 names its own agents' systemd slice, so J5 and T3 Code on one machine don't share one. J5 keeps a queued-run watchdog; retire it if upstream's visible startup failures leave it with nothing to report.
- **Watch for:** upstream closing the race between Stop and an in-flight steer, which J5 no longer guards. With continuation on by default, watch whether it wakes Crew seats and Peer Agents into work their Captain or spawner has already moved past.

## Providers as packages

- **Upstream:** provider code lives in packages. `provider-core` holds the adapter contract, failure handling, the standing instructions, MCP provider sessions, the model catalog, latest-version lookups and the subagent projection. Codex and Claude remain in the server; Cursor, OpenCode (both versions), ACP, the ACP Registry, Grok, Pi and Muse Code are packages of their own. Source-control hosts have moved into packages too.
- **J5:** J5's persona instructions, Crew-seat flag and native-resume fields are edits to `provider-core`, and the native-resume flag is also one line in the OpenCode package. J5's standing instructions live in a J5 folder inside `provider-core`, behind the constant upstream exports ([divergence D1](upstream.md)). Muse Code is taken as an ordinary provider with no J5 work.
- **Watch for:** a way to supply instructions or runtime policy to a provider without editing a package or an adapter, such as an instruction or policy member on `ProviderHost`. That would let J5's package edits go. There is none yet.

## Skills

- **Upstream:** each provider snapshot reports the skills its CLI already has installed (`ServerProviderSkill`), and the composer's slash menu lists them; a slash command or skill can now be searched anywhere in a message, not only at its start. There is no catalog, install, or cross-provider linking.
- **J5:** Settings → Skills installs catalog groups from a configured Git or folder source into Codex and Claude homes, inspects each provider's skills, and links standalone skills across providers.
- **Watch for:** upstream installing or managing skills itself. That would make J5's catalog a source feeding upstream's mechanism rather than a parallel one.

## Playbooks and automations

- **Upstream:** scheduled tasks (Settings → Automations) start or continue threads on an interval, at a fixed time, or from a webhook, through the shared Scheduler. Muse Code brings its own workflow items into the timeline, and Claude's own workflows now show their phases in Lineage. Both are provider-native and keep no progress in the app. Pull requests can get a guided review written by an agent; that is a document, not tracked steps.
- **J5:** Playbooks are step tracking for agent-led work: a workspace library of definitions, persisted runs that agents advance through MCP tools, progress and run history on web and mobile. They carry no scheduling, git, or worktree behavior of their own.
- **Watch for:** upstream workflows or multi-step automations with durable progress kept by the app, which would overlap Playbooks. Upstream has none yet.

## Give-back

Fixes J5 carries that belong upstream are tracked in the give-back backlog. V2 is in upstream's stable release, so they can be offered once the maintainer gives the go-ahead. Upstream fixed one on its own in this range: a revoked session's open sockets now close.
