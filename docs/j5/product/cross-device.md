# Cross-device

## Problem

A person's fleet does not live on one machine. Work agents run on a work server that only the work network can reach; personal agents run at home; a laptop is the client for both. The person wants one inbox and one Fleet page, not one per machine — and eventually wants an agent on one server to be able to ask an agent on another. The prior-art platform tried to replicate identity across machines, never built the transport, and rejected deliveries that were not local ([problems](problems.md): fleet observability, human attention).

## Definition

State can do exactly three things across machines: **authority can replicate, messages can cross, or views can merge.** J5's position is that **authority never replicates.** Messages cross — an Exchange can be delivered from one server to another — and views merge in the client. This avoids replicated identity and multi-master state entirely, and it was built into the communication protocol from the start: delivery is log-first, and a message that crosses projects is two writes, never one transaction, because collapsing them would assume a single host.

The four capabilities, and what each is:

| Capability                                        | Position                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Exchanges between agents on different servers** | Fits the protocol as designed: the delivery pipeline gains a peer step, and the receiving server writes its own received row. What is new is **peering** — the mutual record of which servers may talk, how messages travel between them, and with what credential — defined below. Nothing about addressing changes: an agent names a participant, and the platform knows which server it lives on. |
| **One ledger spanning servers**                   | **A permanent non-goal.** It would require replicated authority or remote execution. A project, its agents and its ledger live entirely on one server; an agent that needs a particular machine runs in a project on that machine, and agents exchange across servers.                                                                                                                               |
| **Merged inbox and Fleet page**                   | **The highest-value, nearest capability, needing nothing server-to-server**: the client already connects to every saved environment at once, and each server's reads merge in the client. Answers route to the server they came from. An unreachable server renders its last-known state with a staleness clock, never as empty and never as fine.                                                   |
| **Any other synchronization**                     | Deliberately none. Worktrees, provider credentials, settings, schedules, cost meters stay server-local by design; views merge their readouts. Role and Crew definitions travel as files. Refusing to sync is the feature.                                                                                                                                                                            |

### Peering

Two servers that may exchange messages are **peer servers** ("peer" alone, in the A2A definition, means another agent). Peering is pairwise and mutual: each server holds a **peer record** for the other — the peer server's environment id and name, how messages travel to and from it, the origin this server reaches it at when it connects to it, the credential the peer server issued for that and when it expires — and each server that is connected to sees the other as one more authorized session in its Connections settings, alongside paired devices and machine tokens, and revocable there like them. The set of a server's peer records is its **peer registry**. There is no directory of servers: a server knows only the peers it has been introduced to.

Messages travel between peer servers in one of two ways, chosen for each pair when it is peered:

- **Send directly.** Each server opens connections to the other and delivers to it. Each record's **link mode** is `push`.
- **Poll.** One server cannot be reached — a laptop behind an office firewall that drops every inbound connection — or may be off when a message arrives, such as a laptop that sleeps, so it opens every connection itself. The reachable server **stores** the messages for it until it **polls** for them, and it sends its own messages to the reachable server directly. The storing server's record of the poller has link mode `store` and no origin; the poller's record of the storing server has link mode `poll`.

A pair's way of travelling changes only by removing the peer and peering again. **Removing a peer wipes the slate** on the server that removes it: any session the peer had there is revoked, every message still waiting to reach the peer is cancelled with a notice to its sender, and every open Exchange with a participant there is dropped with the usual notice. The removal is one write: a message from or for the peer that arrives meanwhile is wiped with the rest or, once the removal is done, refused. Peering again starts empty; nothing cancelled or dropped comes back.

A polling peer is **online** while it has polled within the last two minutes, and **offline** since its last poll after that; a poller polls at least every half-minute while it runs, so its polls are its heartbeat. A poll counts once it reaches the storing server, because a poll held there shows the poller is present. The same rule tells the poller whether the storing server is online, counting each poll the storing server starts to answer.

Servers do not find each other; **the client introduces them.** The client is the one party that is already connected to both environments, so peering is an act taken there. It first checks which way connections can go, by asking each server to reach the other at the addresses that server knows for itself, and how each server is run: one the desktop app runs, or one started by hand, may be off when a message arrives, and a message sent directly to a server that is off fails after a few quick retries. From that it recommends how messages travel in each direction, asks only what the check could not settle, and lets the person set it up differently. It then asks each server that will be connected to for a credential bound to the other server's identity, tells the connecting server where to reach it, and each connecting server confirms it can reach the other before it records the peer server; a storing server records its poller when the poller first presents the credential issued for it. The origin the client itself uses is a hint, not the answer — a loopback or forwarded address that works for the client may not work for a server — so the person confirms the origin to use.

**A server's name is its own.** Each server reports one name for itself, the one every client already shows for it, taken from its machine's name; a peer record carries the other server's current name, refreshed when they greet, poll, or read each other's address book, so agents and every client see the same name. Renaming a server means renaming its machine. Peer servers also state their protocol version on everything they send each other, each side checks the other's, and a server updated past the other's protocol stops exchanging with it and says which server to update, rather than misreading it.

**Agents see where participants live.** An agent addresses a participant by its id exactly as it does locally; the platform resolves the participant to the server it lives on — the sender's own or a peer server. Once a server has a peer, its address book names the server each participant lives on, and whether a peer server that polls this one is available; a send to a participant on a peer server names that server in its result, and the envelope of a message from one names the server it came from. People give their servers different capabilities — Xcode on a laptop, a database connection on a work server — and an agent that can see where each participant lives can pick the right one. No agent tool takes, chooses or manages a server: where a participant lives is a fact the platform states, never one an agent acts on, and which server can do what is the person's to tell their agents.

**A person stays server-local.** A person's participant, their asks, and their inbox belong to each server they use; an ask to a person is delivered on the sender's own server, and the person's view of several servers is the client's merge described above. Peering carries messages between agents, and nothing else.

Delivery across peer servers is the same delivery with one more step: the send is a ledger row on the sender's server, the peer server records its own received row, and that acknowledgement is the sender's delivery receipt. Across servers the receipt means the peer server accepted and recorded the message; delivering it into the agent's thread is then the peer server's own delivery, which retries and alarms there, attributed to the sender as any delivery is. Sent directly, failure to reach the peer server retries and alarms on the sender's server as any failure does. To a polling peer, the message is stored without retrying or alarming until the peer polls for it, and the poller's acknowledgement is the receipt. A message the peer server refuses, or one cancelled before it got there, is reported to its sender. Everything that flows back — a reply, a silence notice, a lifecycle closure — travels the same path in reverse, which is why peering is mutual: one Exchange needs both directions. Peer servers reach each other directly, or one polls the other over connections it opens; a relay or tunnel is never a required part of it.

Peering is also where another person's server attaches, when that time comes — person boundaries, what may cross, and trust live in the peer record, and nothing else in the architecture needs to anticipate other people.

History durability is **client-pulled backup**: each connected client periodically pulls a consistent snapshot from every server it connects to, so the client's existing always-connected fan-out is the backup fabric, with no new infrastructure. Its design — the snapshot endpoint, cadence, retention, restore — is later; the direction is settled.

What this never does: no replicated state, no multi-master, no moving a project's ledger between servers, no global agent registry (peering is pairwise), no server an agent chooses or manages, no dependence on a relay or tunnel (direct peering; a relay could later be one transport among others, never a required service).

## Acceptance criteria

1. A project, its agents, and its ledger exist on exactly one server; nothing moves a ledger between servers.
2. Every person-facing surface that shows fleet state — the inbox, the Fleet page, notifications — merges every connected environment from day one, and each item names its environment.
3. An answer or action taken on a merged surface is routed to the server the item came from.
4. An unreachable server's items render with their last-known state and a staleness clock; they never disappear and never render as healthy.
5. Nothing that is server-local by design — worktrees, provider credentials, settings, schedules, cost meters — is synchronized between servers.
6. Server-to-server Exchange delivery goes through pairwise peering, and the receiving server records its own received row.

### Merged surfaces

7. Environment labels appear on merged items and choices only when the results span more than one environment; a single-environment client shows none.
8. A connection that can only read shows that environment's agents and asks and refuses to create, launch or answer there, with the control saying why.
9. A count over merged environments is marked incomplete when any environment could not be refreshed, and shows no number when none could be.
10. An environment whose server lacks the fleet features is reported as unsupported, never as empty.

### Peering

11. A server delivers to, and accepts deliveries from, only the servers in its peer registry; a peer record names the peer server's environment id, its name, and its link mode, and either the origin this server reaches it at with the credential the peer server issued and when it expires, or that the peer polls.
12. Peering is mutual: the client records each environment as the other's peer server in one introduction, and removing either side ends delivery in both directions. Un-peering is a clean break: a client that can manage both servers removes both sides at once, and one that can manage only this one warns that the other server keeps its side, with Cancel the default and "Remove here only" the deliberate choice. Removing a peer cancels every message still waiting to reach it, with a not-delivered notice to each sender, and drops every open Exchange with a participant on it, with the usual drop notice; peering again starts empty. Adding a peer whose server still holds an old record of this one, such as one left by a removal made on this side only, clears that record first, or names the server to clear it on when this client cannot manage it. An introduction that fails partway stops and reports each step; it leaves any credential it issued unused and the other side's existing credential working, so a retry or a removal clears the half-recorded state.
13. A peer server's credential is an ordinary session of the issuing server, bound to the peer server's environment identity and to a scope that permits only accepting deliveries, polling for stored ones and reading the address book; it appears in Settings → Connections. It is long-lived rather than renewed, and the holder's record shows when it expires. When it is revoked, because the issuer removed the peer or its session was revoked, or it has expired, the holder's deliveries are refused and alarm with that reason, a holder that polls stops polling, the holder's record reads "<server> ended this peering" in either link mode with removal as what is left to do, the issuer's record shows the peer server without a live session, and the address book reports it as unread, never omitted.
14. Peering is done from a client connected to both environments with administrative scope. Before anything is recorded, the client checks which way connections can go and how each server is run, states how messages will travel in each direction, and asks only what the check could not settle; a failed check shows the error it got. The person confirms the origin to use, which may differ from the one the client uses; the server names come from the servers. The client offers a setup only when both servers support poll mode; when either does not, it names the server to update and offers nothing else, while an operator can still peer an older server to send directly from the command line.
15. A peer server that is sent to directly or polled is recorded only after the recording server has reached it at the stated origin with the credential it issued; an unreachable origin is refused with the reason, never recorded, and a known peer server is not moved to a new origin unless the person says so. A polling peer is recorded by the storing server when it first presents the credential issued for it.
16. An agent addresses a participant homed on a peer server by the same participant id it would use locally, and no agent verb takes, chooses or manages a server; once a server has a peer, the address book, send results and envelopes name the server a participant lives on.
17. The address book lists participants on peer servers beside local ones with their project's id and title. It reads the roster of each peer server it sends to directly live on each call, so an unreachable one costs the call its timeout and is reported as unread in the listing, never omitted silently. A polling peer's roster comes from the snapshot it last sent when it polled: current while it is online, "as of" that time while it is offline, and unread until its first poll.
18. A message to a participant on a peer server is recorded in the ledger of the sender's project before the call returns, for a participant the address book resolves or one this server has already exchanged messages with; a first message to a participant on a peer server that cannot be read is refused with the reason. The peer server records its own received row before delivering to the agent's thread, and that acknowledgement is the sender's delivery receipt: it means the peer server accepted the message, and delivery into the thread is the peer server's to retry and alarm on. Failure to reach a peer server sent to directly retries and alarms on the sender's server as any delivery does. A message to a polling peer is stored without retrying or alarming until the peer polls, and the poller's acknowledgement is the receipt; one the poller refuses is reported to its sender.
19. Retrying one message to a peer server, or handing it out again to a polling peer, never yields a second received row or a second delivery.
20. A reply, silence notice, withdrawal or lifecycle closure for an Exchange across peer servers travels the peer path back to the origin server and closes or notifies the origin Exchange exactly as a local one would; a withdrawal closes the Exchange without waking the answerer, locally or across servers.
21. A person is never addressed across peer servers: an ask to a person is delivered on the sender's own server.
22. Peer servers reach each other directly at the recorded origin, or one polls the other over connections it opens; no relay or tunnel is required for peering.
23. A delivery to a peer server carries the sender's display name; the receiving server keeps it with its received row so the client names a remote sender in the timeline as it names a local one, and no agent verb needs it.
24. Every request and answer between peer servers states the sender's peer protocol version, and each side checks the other's, so a mismatch is caught whichever server was updated; a server that states none counts as the first version. A mismatch is refused, naming which server to update, and shows on the peer record until a later exchange between them succeeds. Peer servers also state their capabilities when they greet each other, and a pairing that needs polling is refused before anything is recorded when the storing server lacks it.
25. A message waiting for a polling peer that is cancelled — because its sender was archived, for example — is withdrawn only if the peer has not yet been handed it; one already handed out stays deliverable and its acknowledgement records it delivered. Removing the peer cancels every waiting message, handed out or not. When an Exchange closes whose ask was cancelled before it was delivered or handed out, no closing notice goes to the peer server, which never held it.
26. A server tells its peers what it can do in every greeting, poll and roster answer, and a peer's record keeps the latest. A message sent with `steer` or `restart` crosses with that request and the sender's permission limit only to a peer that says it lands a message as asked; the receiving server refuses it for an agent that runs above the limit.

## Scenarios

- **Two servers, one inbox.** The user's client connects to the work server and the home server. An ask from an agent in Billing Migration (work) and one from an agent in Support Rotation (home) appear in one inbox, each tagged with its environment; answering each reaches the right server. (AC2, AC3)
- **A server goes dark.** The home server is asleep; its rows stay on the Fleet page with "as of 40m ago" and never vanish. (AC4)
- **One server is read-only.** The user's connection to the home server has no operate scope: its agents and asks appear in the merged lists, and the answer box for a home-server ask explains that this connection cannot reply. (AC8)
- **Peering two servers.** The user opens Settings → Connections on their laptop, connected to the work server and the home server, and peers them. The check finds that each can reach the other and that both run as always-on services, so the dialog says each sends to the other directly, at the addresses it proved, and asks nothing; each server confirms it can reach the other at the origin the user confirmed, and each lists the other as an authorized session. Had the home server been run by the desktop app, the dialog would have asked how the work server should get messages to it, with storing them until the home server polls as the default. Revoking either session later ends the peering, and removing the peer from Settings removes it on both servers when the client can manage both, or says which server still lists the other when it cannot. Peering is managed from the web and desktop clients; the mobile client does not manage it. (AC11–AC15)
- **The agent on the Mac.** The user's Mac server has Xcode and the work server does not, and the user's instructions to their agents say so. An agent in Billing Migration, on the work server, needs an iOS build; its address book lists the agents homed on the Mac server beside local ones, each naming the Mac server, so it picks one there and asks it for the build by participant id, as it would ask any participant. The ask is recorded in Billing Migration's ledger, the Mac server records its received row and delivers it, and the reply travels back and closes the Exchange, its envelope naming the Mac server. The agent saw where the other agent lives and never named a server. (AC1, AC6, AC16, AC18, AC20)
- **The home server is asleep.** The home server runs in the desktop app and polls the work server. An agent on the work server asks an agent homed on the home server while the home server's lid is closed. The send is recorded and stored, and its result says the home server is offline and when it was last available; the work server's address book lists the home server's agents as of its last poll. Nothing retries or alarms. When the home server wakes, it polls, receives the ask and acknowledges it, and the reply comes back directly. A first message to an agent the home server had never listed when it last polled is refused, naming that as the reason. Had the two servers been peered to send directly, delivery would retry and then alarm on the asker, and the address book would report the home server as unread. (AC17, AC18)
- **A laptop behind an office firewall.** The user's work laptop sits behind a firewall that drops every inbound connection, and its work server is always up. Peering them from the laptop, the check finds the work server cannot reach the laptop, so the dialog says the laptop sends messages to the work server directly, and the work server stores messages for the laptop until the laptop polls for them; it asks nothing. The work server records the laptop when the laptop first presents its credential. From then on the laptop opens every connection: an agent on the work server that asks an agent on the laptop has its ask stored and picked up within seconds while the laptop is awake, and an archive on the laptop reaches the work server's address book on its next poll. When the work server's agent messages an agent the laptop archived after its last poll, the laptop refuses it when it polls and the sender gets a not-delivered notice. (AC14, AC15, AC17, AC18, AC22)
