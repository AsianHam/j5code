# Crews

## Problem

Complex work needs a group of agents with defined jobs working together with a high degree of independence from the person — a builder, a reviewer, and a sitter on one pull request is the canonical case. Wiring such a group by hand every time is slow and error-prone, groups that die leave stranded obligations, and a Foreground agent that keeps the person's attention needs somewhere to hand context-heavy work so it can stay responsive ([problems](../problems.md): large unsupervised groups, human attention, more work needs more cleanup).

## Definition

A **Crew** is a group of agents formed as a unit from a **roster its Captain proposes, approved by the person by default**, composed for the brief in front of it. Nobody writes a Crew file in advance. The person asks the agent in an ordinary conversation to compose a Crew (web and desktop). The agent uses the conversation as context, keeps its current persona, model, and policy, and proposes the team before starting its work. There is no Crew slash command. No dedicated Captain agent exists; the agent that proposes becomes the Captain. It proposes a roster — a name, the brief every seat will start on, and a responsibility with a reason and instructions for each member. Saved personas are optional templates; a roster can mix them with custom members. A seat may name no persona at all: a **custom seat**, named and briefed by the Captain or the person, defaults to the Captain's provider, model, and reasoning but to Full access, with harness, model, reasoning, and access editable before approval, so a Crew need not fit a mold anyone saved before (Jackson and Bryant, 2026-09-17). The Captain's access is never carried: a seat nobody configured would otherwise stop for approvals in a thread the person is not watching (Jackson, 2026-09-26). Its instructions are required at every door, since nothing else defines it. By default the proposal is a **human gate**, answered inline above the Captain's composer and never on the Inbox bell. **Settings → Agent Setup → Crews → Auto-approve new Crews** skips that gate when enabled for the Captain's project; it is off by default with project overrides. The setting is read for each new request, and changes leave existing Crews and open proposals alone. The Captain is the thread the person watches, so its own tool approvals and questions are answered inline there too. A seat runs out of view, so its provider tool approvals are answered from the Inbox (Jackson, 2026-09-26). A seat has no native question tool: when it needs a decision it asks its Captain with `j5_send_message`, and the Captain answers, or asks the person with its own question tool, inline in the Captain thread (Jackson, 2026-09-26). Claude seats run without `AskUserQuestion` and Codex seats without `request_user_input`; Cursor exposes no structured native question tool. Other harnesses keep their native tools and the standing rule to ask the Captain. If a seat still raises a native question, its Captain receives a queued notice naming the question and its thread. The person also sees a link in the Inbox to answer in the seat's original question form (Bryant, 2026-10-19). The person may drop seats, select personas from the library, or create custom seats with names, instructions, and runtime settings. Every proposed or manually added member uses the same editor before approval. Saved personas supply defaults; the person may override harness, model, reasoning, and access for this member without changing the saved definition. Approval creates every seat as a Peer Agent placed under the Captain, with a persona assignment only when the seat names a saved definition, and records the roster snapshot (the _Manifest_ in implementation vocabulary: name, brief, members with each one's reason and version). It starts no provider turns. The Captain receives a creation report naming what the person changed and which seats were created or failed. A decline is told at once. Each seat's first delivered assignment carries the platform's identity facts, the current Crew context and roster, any seat instructions, a handoff artifact obligation when its definition declares one, and the approved brief.

**Captains add members directly.** When the work needs expertise the roster lacks, the Captain adds one seat with a reason and optional brief. No human approval is needed, regardless of the auto-approval setting. The same launch checks apply; the tool returns the updated roster or a refusal naming the member and reason, and the launch report follows. A Crew holds at most **twelve seats**, counting open legacy requests. Members escalate staffing needs to their Captain. Pending addition requests from before this change remain approvable or declinable above their Captain's composer and stay off the Inbox and its bell.

**Configured access controls tool approvals.** A seat runs with its proposed configuration, or the person's final configuration when a human approves it, using its persona's policy when no override is selected; the Captain may be read-only. The gate shows each seat's persona or custom-seat choice, instructions, and resolved harness, model, reasoning level, and access before approval, and the Captain's reason for a seat stays readable in its row. Human-approved rosters and legacy additions use the same preview. Automatically approved rosters and direct additions use the proposed configuration through the same runtime validation; their history records automatic approval. Automatic approval never changes a seat's tool approval policy. A custom member started automatically, by an auto-approved roster or a Captain's addition, defaults to Full access like any custom seat, so a Supervised Captain can start a Full-access member without review; that is accepted (Jackson, 2026-10-31), and the Agent Setup setting governs rosters only. Approval binds the displayed roster and configuration; changed configuration requires a fresh review, and a launch uses the validated resolution rather than choosing a different route afterward. Seats are checked where they are structured: a persona missing from the library or turned off, a duplicate seat name, or a roster past the cap is refused to the Captain with the next step, before anyone spawns. Prose in a brief is never parsed or validated.

**Several people.** Where more than one person can write to a Captain's thread, "the person" in this definition is any of them. The roster and a seat's tool approvals go to everyone who can write to that thread, and the first answer settles each; anyone who can write to the Captain's thread can write to its seats too ([shared conversations](shared-conversations.md), [people and access](people-and-access.md)).

**Communication is direct; handoff artifacts record durable outputs.** Members exchange findings, questions, blockers, and results directly with one another and their Captain; Captains can coordinate with other Captains. Neither an artifact nor a human approval is required for these messages. Members send their final result with evidence and unresolved issues to the Captain. Active Codex GPT 6 and Claude runs accept peer steering, Claude once its running tool calls finish; other models and providers queue messages until the next safe turn boundary. A seat whose persona declares an output artifact (a Critic's ReviewHandoff, a Scout's ContextBrief) owes it as the same shared handoff artifact every persona writes — `handoffs/<agent>/<Artifact>-<task>.md` in the project's artifacts (see the [persona contract](../agent-personas/index.md)) — and its first turn names that exact path. The handoff gate checks for the file when a run ends and reminds the seat once. File existence is evidence of delivery, not validation or acceptance of the result; the Captain reviews the handoff artifact against the task. **Every seat tells its Captain when it finishes**, as measured facts: how the run ended first, the run's error when it failed, and whether its handoff artifact was written, missing, unavailable (with why), or never declared, with the artifact inline when short. A first turn that fails is a launch outcome, told once by the launch report and not again as a finish; and a seat's failure that its Captain hears this way is not repeated by the silence detector as an unanswered ask. The notice is posted the first time a seat finishes and again only when those facts change; a finish that would repeat the last notice word for word is silent, because the seat's own reply already reached the Captain. Notices that arrive while the Captain's turn is running fold into the one seat notice already queued behind that turn, so the Captain absorbs its Crew's news in one turn rather than one per seat. Notice delivery retries on a later finish or the next server startup if dispatch fails; it is not guaranteed promptly while the seat stays idle. Sign-in and permission failures also raise a platform notice in the person’s Inbox, with replies routed to the Captain; other failures remain for the Captain to assess. A Captain normally does not have to interview its Crew to learn a seat is done, and it never waits for one inside a turn: `t3_thread_wait` is not on its surface, because a turn that blocks cannot receive the notice it is waiting for. The person opens every handoff on the Artifacts page. A direct result message does not replace a handoff artifact explicitly required by a saved persona.

**Members report their finish.** When a member's run ends and it owes no open reply, the platform tells its Captain how the run ended and where its handoff artifact stands; a later message runs normally. The platform never settles a seat because its run finished: upstream settles by hand, by merged PR, or by idle days, and a seat marked settled seconds after launch read as wrong (Jackson, 2026-09-17). Settling the Captain settles its seats (AC17). **A Crew's state is its seats' states**, summarized from measured facts — how many seats are running, need a person, or were settled — on the Crew's row of the Fleet page and on the Captain's expander in the sidebar, where each seat's row also says how its last run ended (failed, interrupted, or completed); the person never has to interview a Crew to learn where it stands. **The Captain's timeline keeps approval compact and shows what needs attention.** The launch report and finish notices reach the Captain unchanged, but the person sees one line per seat that couldn't start, was never created, hasn't confirmed it started, failed, or finished with its handoff artifact missing or unreadable, each opening the seat's thread when it has one; a roster approval shows “Crew approved · N members” from the stored gate notice, including in existing threads; a clean finish shows nothing, and an interruption after the first turn, which comes from a stop, is silent there too. Members stay out of the thread sidebar unless pinned; the Captain's row carries the Captain's anchor mark and an expander into its members; the Fleet page lists every agent by project and placement with each Crew under its Captain. Crews are a web and desktop surface; mobile has no Crew surface today, deliberately.

### Captains

Any agent with Crews placed under it is a **Captain** — a derived, measured status, not a platform entity or a tier. The management layer is made of agents in the placement tree, which nests to any depth; there is no container above the Crew.

- **Any harness can captain.** A thread on any provider T3 Code ships — Codex, Claude, Cursor, Grok, OpenCode, Antigravity, Pi, or an ACP registry harness — can propose and command a Crew, and a seat on any of them works the same way. J5 pre-approves its own tools on Codex and Claude only, so there the roster card is the only human step before a Crew launches: proposing, requesting a member, and messaging never wait on the harness's own approval, whatever its runtime mode. Other harnesses may ask once with their own MCP prompt before the roster card, and a read-only persona on them can't propose (Jackson's ruling, 2026-09-26). The platform's other verbs follow the thread's policy the way Codex does: where the thread never asks for approval they run freely, and elsewhere the harness may ask.
- **You command what you brief.** The Captain that proposed and briefed a Crew commands it. Proposing a Crew _for_ someone else is proxy management; instead, send the decision and the brief to the future Captain.
- **One Captain, many Crews.** Concurrent work gets concurrent Crews: a Captain may propose another Crew whenever the work splits, each through its own gate and named for what it is for, and every later request, stop, and archive names the Crew it means. The Captain's expander in the sidebar and its node on the Fleet page show one named, collapsible group per Crew.
- **Agents run Crews.** Captains coordinating Crews without the person in the loop is the point; the person's part is the gate. A member's attempt to grow or archive a Crew, or to spawn a Peer Agent of its own, is refused with an error naming escalation to its Captain; a member that needs a helper runs a provider-native Subagent inside its own session (Bryant, 2026-09-14, closing the question left open on 2026-08-24).
- **A Captain may stop the Crews directly under it.** `j5_stop_crew` interrupts every seat with a running turn and leaves idle seats alone; nothing settles, nothing is retired, and every seat can be messaged again. The person has the same act as a Stop crew control on the Crew's Fleet header and on the Captain's sidebar expander, offered only while a seat is running.
- **A Captain may archive the Crews directly under it** — the only agent-invoked archive, and it triggers the same loud machinery as any archive. Not grandchild Crews, not individual members, not solo agents. The person has the same Archive crew act on the Crew's Fleet header.
- **A Crew follows its Captain.** There is never a Crew without its Captain (Bryant). When a person archives or deletes a Captain thread from any surface, the platform retires the live Crews it commands as units the moment the archive commits, the web dialog having shown every live Crew seat by seat beforehand; unarchiving the Captain, or Undo on its archive, brings back the Crews that retired with it, seat threads included. Undo and unarchive don't restore interrupted runs or dropped Exchanges. If an unarchive stops partway (some seats back, the Crew still retired), the person archives the Captain again and unarchives it, or clicks Undo; that re-runs the restore, which skips seats already unarchived. Settling a Captain, by hand or by upstream's automatic settlement, settles every seat of its live Crews except one still running or waiting on the person, which upstream's automatic settlement would leave alone too; unsettling it unsettles the seats that were settled. A Crew retired on its own through Archive crew or `j5_archive_crew` stays retired when its Captain comes back.
- **Captains are never routers.** Any participant may message any participant; the hierarchy carries decisions, never messages.
- **A Captain's runtime policy does not gate the platform's verbs.** Stopping, archiving, and retiring what it commands are decided by identity (only the Captain, only its own Crew) and by the human's confirmation, never by the Captain's sandbox: a read-only Captain runs its Crew's lifecycle like any other (Bryant, 2026-09-14). The sandbox guards the workspace; the platform guards its own verbs.

### Lifecycle

Crews are deliberately disposable. They **archive only as a unit** — members are never individually archived or replaced — because an agent's death is usually recoverable by messaging it again, and an irrecoverably poisoned member has likely contaminated its crewmates. Recovery is **propose again**, which is cheap because a Background Crew's value lives in its brief, its approved roster, and its durable artifacts — worktree, branch, pull request, handoff artifacts — which survive the agents. Two platform rules make this safe: archive never destroys work, and archive is loud, with every open Exchange ending in a notice to its waiter. A former seat unarchived on its own through the ordinary unarchive is a solo agent, not a member of any Crew; a Crew comes back only with its Captain.

**Archive and respawn are judgment moments, and the platform never makes that decision itself.** Archiving a Crew with open Exchanges or running turns refuses with the list, seat by seat, and requires a confirmation token; the expectation, carried in guidance rather than enforced, is that a Captain checks with the person and they plan together. The successor Crew starts from a fresh proposal and a fresh brief written by whoever respawns it — where things stand, the state of the durable artifacts, what to do next. There is no auto-forwarded original brief, no generated summary, no transferred conversation, no inherited obligations, no auto-reopened asks; the archived Crew's brief, roster, ledger, and handoff artifacts stay readable for the respawner to consult.

The platform ships the machinery — propose, gate, spawn, render, remind, notify, archive. The Captain agent that composes a Crew, the personas it seats, and any Playbook it follows are always the user's content: the PR Group is one Captain's proposal someone approved, never the product's opinion.

## Acceptance criteria

### Launch and the gate

1. Asking for a Crew in ordinary chat causes the current agent to propose a roster before doing the delegated work. The thread retains its persona, model, and policy; saved personas are optional and there is no Crew slash command.
2. Initial roster proposals start collapsed in a compact strip above the Captain’s composer, alongside Tasks and Playbooks. Expanding or collapsing the strip is remembered for that thread and environment; the roster draft survives collapsing and the strip leaving while the composer shows an approval or a question, until the person decides. The person reviews the outcome and members, adds or removes members, edits a member in a modal, and approves or declines the final roster. Add and Edit share the same modal: Cancel discards that modal’s changes, while Save validates the member and returns to the roster. Invalid or duplicate names and missing custom-member instructions prevent saving. The last member cannot be removed. Approval is unavailable while a modal is open or a matching full-roster preview is missing. With Auto-approve new Crews enabled for the Captain’s project, it launches as proposed with no card.
3. Each proposal member shows its provider, name, model, reasoning, access, and the Captain’s reason. Non-shared workspaces and access that stops for approvals remain visible. The Persona picker offers Custom member and the available saved personas. Selecting a saved persona populates its name and instructions and resolves its runtime defaults; the saved definition is unchanged. The instructions box holds the persona’s whole text, and an edit replaces the persona’s instructions for this member only; the original is not also sent, and Reset to persona text returns the box to the saved text. The instructions an agent attaches to a persona seat stay additional, and an unedited box keeps them. Runtime and workspace choices remain editable. A new custom member starts in the Captain’s checkout. Existing and new worktrees use the Captain’s repository options. Editing the roster refreshes the server preview, which binds the exact runtime settings, Captain’s project and checkout, each seat’s workspace, and the current playbook plan. Missing, unavailable, incomplete, or stale previews cannot approve a launch. Playbook proposals retain each member’s steps, persona-swap explanations, and unowned steps for the Captain. The card cannot reassign steps; removing a member leaves its steps unowned.
4. A seat naming an agent missing from or disabled in the library, a duplicate seat name, or a roster past twelve seats is refused to the Captain with the next step, before anything spawns; prose is never parsed. So are an unknown or invalid playbook, a step the playbook lacks, a step claimed by two seats (or already owned by a live member), and steps on a Crew without a playbook. A seat that claims no steps needs no readable playbook, so a Crew whose playbook file is gone can still grow. Each step has one owner, enforced again where member rows are written, so of two additions racing for one step the first reservation wins and the second is refused.
5. New Crew proposals require human approval unless the Captain's project enables auto-approval. Additions run directly without approval. On Codex and Claude, under every sandbox, approval policy, and runtime mode, including Codex approval policy `never`, `j5_propose_crew`, `j5_request_crew_member`, `j5_send_message`, and `j5_clear_own_ask` reach the service or their recipient with no other human step and are never refused. On every other shipped harness they may first raise that harness's own MCP prompt once, and a read-only persona there cannot propose. Where the thread never asks for approval (full access, or a saved persona whose policy resolves to never), spawning, stopping, and archiving, `j5_write_artifact`, and the delegated-task verbs also run without a prompt; in interactive modes the harness's own approval may apply to them.

### The unit

6. Approval creates every seat as a Peer Agent placed under the Captain and records the roster snapshot with each member's reason (human or automatic approval is recorded); it starts no turns. A proposal resolves once, so a second approval creates nothing and a decision racing another device's answer is refused. The Captain receives one launch report immediately after creation, naming the person's changes, each created seat as waiting for work, and any creation failures. A seat whose provider is signed out is refused before creation. The first participant message, direct chat message, or playbook step activates a waiting seat with its approved instructions and shared brief, the roster at activation including responsibilities and participant ids, and the assignment with its envelope and reply obligation intact.
7. An approval launches once. A failure before any seat spawns (the Crew or the approval could not be recorded) leaves the gate open to approve again; once seats start spawning, a seat that fails does not stop the others, and the launch report names every approved seat, including one whose thread was never created. A seat that was never created is not on the roster; the Captain asks for it again with `j5_request_crew_member`.
8. A Crew lives in exactly one project and renders as one node under its Captain with its members beneath it.
9. Every member can message any participant; the Crew's contact with the person goes through the inbox or its Captain rather than chat — a plain send to the person is refused by the [human-ask rule](../a2a/agent-tools.md), so a seat reaches the person only with an ask that lands in the Inbox or a reply on an open Exchange. A live Crew seat's pending provider approvals that the provider can still take are listed in the Inbox with their Crew and seat, counted on the bell, and answerable there; the seat's own thread still shows them too, so either place may answer. The Captain's approvals and questions, and approvals a seat can no longer take, are not listed. A live seat's pending native question that can still take an answer is listed as an Inbox link and counted on the bell; it is answered in the original thread, and the link disappears when resolved. A seat asks its Captain rather than the person: Claude and Codex seats have no native question tool, and every seat is told to ask its Captain with `j5_send_message`; a harness that still lets a seat ask natively shows the question in the seat's thread and notifies its Captain. The Captain may answer through upstream's pending-request tools when its modes allow and the answer follows the brief or the person's instructions; otherwise it asks the person to answer in the seat's thread. Native questions are not Inbox Exchanges. An answer to a request already resolved elsewhere is refused and changes nothing.

### Growing

10. Only the Captain adds members, directly with a reason and assignment, regardless of the auto-approval setting. The same launch checks apply; successful additions create a waiting seat without a turn, append it to the roster, and bump the snapshot version. The tool returns the updated roster or a refusal naming the seat and reason. No new addition request waits for a human; open legacy requests remain resolvable above their Captain's composer.
11. A Crew holds at most twelve seats, counting open requests; a member's request is refused naming escalation to its Captain.

### Handoff artifacts

12. A seat whose definition declares an output artifact writes it as its handoff artifact in the project's artifacts; its first turn names the exact path. The first assignment carries its playbook context and handoff obligation; a later assignment reuses the same thread and workspace without repeating its introduction, unless the provider conversation was replaced (a model or provider switch, or a native session the provider lost), in which case the introduction is sent again with the current roster. Members that finished remain available on the roster. Started members receive net roster changes, naming who joined or left and their responsibility, at the top of their next delivery, including a message steered into a turn in progress. Waiting members receive the current roster with their first assignment. Context is attached at provider delivery, after queued edits, cancellations, and reordering; a start that never reaches the provider, because it was refused, stopped, or superseded, leaves it owed. A waiting member whose Crew retired must have its Crew restored before starting, and a worktree seat cannot fall back to the project root. What a member was told is kept in its own thread: once the provider has taken a prompt that carried the introduction or a roster change, the thread gains a collapsed card, **Introduction** or **Roster changed**, that opens to the text the model read, without the assignment. The card sits with the run it was told in, starts no run and queues none, and is posted once however often a delivery is retried; a refused or superseded send posts nothing. Roster changes alone start no turns, and availability produces no polling or acknowledgment turns.
13. When a seat finishes, the Captain receives a notice that leads with how the run ended and, for a failed run, carries the run's recorded error, then whether the seat's handoff artifact was written, missing, unavailable with the reason it can never be read, or never declared, a written handoff artifact riding inline when short and by path otherwise; a finish whose notice would repeat the seat's last one is silent, and a notice arriving while the Captain's turn runs folds into the seat notice already queued behind it rather than queuing another turn.
14. A seat that finishes without its handoff artifact is reminded once and is reported to its Captain on its next finished run whatever happened.

### Captains

15. A Captain shows the anchor mark, derived from placement and nothing else, with the Crews it commands in its tooltip; each Crew it commands renders as its own named, collapsible group with that Crew's state summary, and solo agents it spawned sit in a separate group; members stay out of the sidebar unless pinned.
16. A Captain may archive a Crew placed directly under it and nothing else; a member's attempt to grow or archive a Crew, or to spawn a Peer Agent, is refused naming escalation to its Captain. Members may still run provider-native Subagents.
17. A Crew follows its Captain: a person's archive or deletion of the Captain's thread, from any surface, retires the Crews it commands as units when it commits, and the web dialog lists each live Crew's seats with their running turns and open asks before the person confirms; unarchiving the Captain brings back every Crew that retired with it, seat threads included; settling the Captain settles every seat of its live Crews that is not running or waiting on the person, and unsettling it unsettles the settled seats. An archive or deletion the event stream missed while the server was down retires the Captain's Crews at the next boot; an unarchive, settle, or unsettle it missed is not caught up. The person can also retire one Crew from its Fleet header behind the same seat-by-seat dialog, and a seat can never be archived on its own from the app.

### Lifecycle

18. J5 never settles a seat because its run finished; settling the Captain settles its seats; upstream's settle rules apply to every thread.
19. A Crew archives only as a unit; archiving never deletes a worktree, branch, or checkpoint; archiving with open Exchanges or running turns lists them seat by seat and requires a confirmation token.
20. A successor Crew starts from a new proposal and a fresh brief; nothing from the archived Crew's conversation, obligations, or asks is carried over automatically, and its brief, roster, ledger, and handoff artifacts stay readable: the Fleet page's Retired section lists retired Crews across projects, each naming its project, with a link to the Captain's thread while it is active (the ledger's home), the brief, the roster snapshot (seat, agent, why it joined, version), the version, and when it retired, and offers no action on them; a retired Crew comes back only with its Captain, when it retired because the Captain was archived (AC17); handoff artifacts stay on the Artifacts page.
21. A Crew stops as a unit: its Captain over `j5_stop_crew`, or the person from the Crew's Fleet header or the Captain's expander, interrupts every seat with a running turn; idle and not-started seats are untouched, nothing settles or is retired, and the result names each seat as interrupted, already idle, or archived.

### State

22. A Crew's Fleet row and Captain's expander summarize measured seat states, including Not started separately from idle, running, failed, needing a person, settled, and unknown. Not started means creation succeeded and the seat is still waiting for its first assignment; a seat whose first start ran and failed or was interrupted reads that instead. Stop, archive, settle, and unarchive treat waiting seats as idle seats. A failed last run reads as failed; nothing is inferred from silence. A seat with a finished run still reads Failed, Interrupted, or Completed. In the Captain's timeline, a roster approval shows “Crew approved · N members”, plus “· by <name>” in a shared conversation, where more than one person could have approved it; other notices show a line only for a seat that needs attention. A clean finish adds no line.

### Several people

23. Where more than one person can write to a Captain's thread, a seat's approvals are listed in the inbox of each of them, the first answer settles each, and each of them can message, stop and answer the prompts of the Crew's seats.

## Scenarios

- **A pull-request Crew.** In Billing Migration the user sends "Put together a crew to land the invoice-export PR: build, review, sit on CI." The Captain proposes Builder, Critic, and Sitter with a reason each; the user drops the Sitter, approves, and the two seats appear under the Captain as Not started. The Captain sends the Builder its assignment, then sends the Critic the review assignment when code is ready. Each receives the brief and current roster on activation. The Critic finishes and writes its ReviewHandoff into the project's artifacts; the Captain's thread receives the notice with the findings inline. (AC1, AC2, AC6, AC8, AC12, AC13)
- **Two Crews at once.** In Website Redesign the user, mid-conversation with the agent that has been planning the launch, sends "Create a crew to migrate the blog to the new CMS" and then "Create another crew to rewrite the pricing page copy". The same thread proposes two rosters, each answered above its composer; both appear under the Captain's row as named groups, Blog Migration and Pricing Copy, each with its own toggle, state, and Stop. (AC1, AC2, AC15)
- **More hands.** The Captain adds a Sitter for the CI failures directly; the seat joins at version 2. A signed-out provider instead refuses the named seat without adding it. A Builder trying to add a helper is refused and told to escalate to its Captain. (AC10, AC11)
- **A flaky launch.** One of three approved seats cannot be created when the user approves the roster. The other two wait for assignments; the launch report says the third was never created and why, and the Captain asks for it again with `j5_request_crew_member`. (AC7)
- **Stop everything.** The Builder is heading down a path the person recognizes as wrong while the Critic is mid-review. The person clicks Stop crew on the Crew's Fleet header; both running turns end, the seats stay on the roster, and the Captain briefs them again. (AC21)
- **A playbook-shaped Crew.** After talking through a change with the agent, the user sends "ok, lets create a crew to implement what we have discussed. Please use @playbook:release for this work." The agent reads the playbook and proposes a roster above its composer: "Follows playbook: Release", a planner seat and a builder seat each owning the steps that name them, the step that names no persona placed with the builder, and a stand-in custom seat for the turned-off reviewer persona, flagged as a swap. The user approves; the launch report names the playbook, the Captain starts it, and the first step reaches the planner seat. Asking for "the release playbook" by name does the same; a message that only mentions the playbook in passing gets an ordinary roster. (AC1, AC2, AC3, AC6)
- **A poisoned Crew.** The Critic has gone wrong and confused its crewmates. The Captain asks to archive the Crew; the refusal lists two open asks and one running turn seat by seat with a token; the Captain confirms after checking with the user, writes a fresh brief from the surviving branch and handoff artifacts, and proposes a successor. (AC16, AC19, AC20)
